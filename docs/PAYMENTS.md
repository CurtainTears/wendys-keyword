# 支付宝售码

KeyWord 正式售卖普通账号注册邀请码，固定 **990 分（¥9.90）/ 个**；独立沙箱的新测试订单固定 **1 分（¥0.01）**，仅模拟资金。付费码一次性使用、未使用前长期有效；手工发码继续使用原有 1–365 天有效期，默认 7 天。已有账号不需要重新购买。

## 先配置，再开放有限销售

`ALIPAY_MODE` 默认 `off`。没有配置或配置无效时，登录、手工发码、私人词库与练习保持可用；管理员页显示支付未配置或配置错误，购买接口拒绝下单。

配置有效也不会自动开售。管理员在“管理 → 在线售码”设置当前可售余量并勾选“开放购买”，保存后生效。余量不含已售出和待付款占位；保存携带版本号，销售或关单期间数字变化会要求刷新，避免覆盖库存。暂停销售只阻止新订单，不阻止已有订单付款、查询和领码。

每笔订单占用一个名额，付款确认后发一个码。付款链接有 30 分钟绝对期限。关闭请求及过期订单由服务端查询并关单；只有支付宝确认关闭，或绝对期限结束后查询确认交易不存在，才恢复余量。每分钟自动核对最多 20 笔过期订单；外部服务不可用时保留占位并提示稍后查询。每个来源地址每小时最多创建 5 笔订单。

### Nginx Proxy Manager 后按真实访客限流

所有者使用反向代理时，应设置 `TRUSTED_PROXY_CIDRS`，填写 **KeyWord 实际看到的代理连接源 IP**，多个地址或 CIDR 用逗号分隔。优先使用单个 IPv4 `/32` 或 IPv6 `/128`；只有整个网段均由可信代理组成时才使用网段。容器部署中的连接源可能是网桥地址，不能直接假定为 NPM 容器 IP 或 `127.0.0.1`。Compose 会把此可选配置传入应用。

该配置同时用于购买和登录/注册限流：默认留空，不采信任何转发头；只有连接来自配置中的代理时，才从 `X-Forwarded-For` 的右端沿可信代理链向前解析，遇到第一个非可信地址即作为访客来源，不信任客户端伪造的左侧前缀。IPv4 映射地址和不同 IPv6 写法会规范成同一来源。`X-Real-IP`、`Forwarded` 和客户端自填的内部来源头不会覆盖这一结果。

此逻辑兼容 NPM 官方[默认代理配置](https://github.com/NginxProxyManager/nginx-proxy-manager/blob/develop/docker/rootfs/etc/nginx/conf.d/include/proxy.conf)追加实际来源、[自定义 location 模板](https://github.com/NginxProxyManager/nginx-proxy-manager/blob/develop/backend/templates/_location.conf)覆盖为实际来源的两种写法。所有者需确认自己的代理确实保留或追加真实连接地址，不能原样透传未经处理的客户端头。多层代理只信任实际受控节点；不要把访客网段或全部公网设为可信代理。配置不接受主机名、`*` 或 `/0`；无配置或非可信连接仍按直接连接来源限流；转发地址无法继续解析时保留最后已确认的连接/代理来源。这些情况下代理后的访客仍可能共用额度。

## 沙箱使用独立数据

官方 Skill 准备的项目根 `.alipay-sandbox.json` 必须保持 `0600`，由服务端直接读取，不复制密钥到源码、其他配置或日志。该文件被 Git 与镜像构建排除。沙箱不能在 `NODE_ENV=production` 进程中启用，也不读取生产配置。

使用独立测试目录与本机端口，例如在未占用的测试端口启动：

```sh
npm run build
ALIPAY_MODE=sandbox DATA_DIR=./.cache/alipay-test PORT=57393 APP_ORIGIN=http://127.0.0.1:57393 node server.js
```

首次在该测试目录初始化管理员邀请码，然后注册、登录管理员，在页面设置有限测试余量：

```sh
DATA_DIR=./.cache/alipay-test npm run invite -- create --admin
```

打开 `http://127.0.0.1:57393/payment/return`，创建订单并进入官方沙箱收银台。使用官方分配的沙箱买家账号与测试密码；仅使用模拟资金。页面会明确显示“沙箱”与 0.01 元测试价，不使用正式支付宝扫码。需要付款确认时由用户本人在网页测试账号流程中提交。回跳与浏览器显示均不能证明付款，必须等服务端可信查询确认后领码。

本机沙箱没有公网通知地址时省略 `notify_url`，结果页通过主动查询补偿。公网通知联调和生产应用配置由站点所有者上线时完成。沙箱账户、密码、密钥和签名链接不要提交到仓库或普通日志中。

## 生产配置由所有者挂载

所有者在官方平台完成签约、应用发布与密钥配置，并在项目目录和镜像之外准备仅容器运行用户可读的 `0600` JSON 文件。字段为 `appId`、`privateKey`、`alipayPublicKey`、`sellerId`；均属于同一生产应用及收款方。Node.js 使用无 PEM 头尾的原始 PKCS#1 私钥。生产私钥不交给聊天代理处理。

启动时设置以下非秘密配置，并将该文件只读挂载到对应路径：

```text
ALIPAY_MODE=production
ALIPAY_PRODUCTION_CONFIG=/run/secrets/alipay-production.json
```

默认同步回跳为 `APP_ORIGIN/payment/return`；默认通知为 `APP_ORIGIN/api/payments/alipay/notify`。生产要求 `APP_ORIGIN` 为 HTTPS，通知也必须是同站精确 HTTPS 路径，不接受其他地址、查询参数或重定向。`ALIPAY_NOTIFY_URL` 仅用于显式指定这一地址。

基础 Compose 不强制支付配置。所有者可在自己的 Compose 覆盖文件中添加上述两个环境变量和只读密钥文件挂载；让容器的 `node` 用户能够读取，且保持文件权限 `0600`。不要把密钥加入 Dockerfile、镜像、GitHub 构建参数或 Actions 日志。修改配置后由所有者更新自己的服务，保留原 `DATA_DIR` 和 `BETTER_AUTH_SECRET`。

生产收款前必须实际核对：产品签约和应用状态、同一应用的密钥与收款方、通知公网可达、验签及关键字段、重复通知不重复发码、纯文本 `success` 回写、漏通知时查询补偿，以及备份恢复。源码发布及镜像构建不等于这些项目已完成。

## 订单、领取与退款

- 前端不提供可信金额、权限或商品参数。服务端按运行环境固定正式 990 分、沙箱 1 分，并固定普通账号权限；校验与退款使用订单原金额，不因切换测试价改写旧单。
- 买家在下单前生成并保存独立的 256 位随机领取凭据；数据库仅保存散列。每次读取、继续付款、查询或关单都核对该订单的凭据，放在请求头而不是 URL。知道订单号或登录其他账号都不能领取此订单。
- “保存领取凭据”下载的文件仅用于恢复该订单；不要转发。清空浏览器前先保存它。遗失后需向管理员提供支付宝订单信息核对，不自动认领其他浏览器的订单。
- 回跳参数会从地址栏移除，不据此选择他人的订单或发码。结果页只使用本机保存的领取凭据定位原订单，并请求服务端查询。无订单上下文时显示中性购买页面。
- 支付查询使用 SDK 响应验签；通知使用完整表单参数与 SDK 验签，核对当前应用、收款方、订单号、金额、交易号和状态。退款等事件不当作付款成功。
- 发码、订单状态与通知幂等记录在同一 SQLite 事务提交。重复通知、查询、重启不会重复发码。所有支付数据库操作与 Better Auth 共用互斥队列，支付宝网络请求在队列之外。
- 邀请码加密方式与管理员发码相同，使用或撤销后删除可回显的密文。恢复数据库必须同时保留原登录密钥，否则无法恢复完整码。
- 管理员仅能发起未使用码的全额退款，不提供部分退款。界面再次确认金额和撤销后才提交；网络异常或结果未知时保留相同退款编号、金额与原参数重试，并暂停邀请码。间隔至少 10 秒查询；确认退款成功才撤销码、恢复名额。已注册使用的码不能走此自动退款接口。

## 接口

购买接口只开放必要范围，其余词库、练习和管理内容仍要求登录。修改请求保持同源校验；只有精确的支付宝通知 POST 路径例外，由签名与业务校验保护。

- `GET /api/purchase/status`：是否配置、环境、固定价格、是否可售；不列出订单。
- `POST /api/purchase/orders`：`{ requestId, receipt }`，同一请求和凭据幂等下单。
- `GET /api/purchase/orders/:id`：查询本地订单，要求 `X-Keyword-Receipt`。
- `POST /api/purchase/orders/:id/pay|refresh|close`：继续付款、支付宝查询补偿、请求关单；要求领取凭据与 JSON 对象。
- `GET /payment/return`：无需登录的结果页壳；不相信同步结果参数。
- `POST /api/payments/alipay/notify`：支付宝表单通知，成功处理才返回纯文本 `success`。
- `GET /api/admin/payments`：当前支付环境的库存和最近 100 笔订单；不返回领取凭据或完整邀请码。
- `POST /api/admin/payments/stock`：`{ enabled, available, version }`。
- `POST /api/admin/payments/:id/refresh|close|refund|refund-query`：管理员核对、关单、全额退款、退款查询。退款要求按订单金额明确确认：正式 9.90 元订单使用 `{ confirmation: "退还9.90元并撤销未使用的邀请码" }`，沙箱 0.01 元订单使用 `{ confirmation: "退还0.01元并撤销未使用的邀请码" }`；其余动作使用 `{}`。

沙箱和生产按环境及应用 ID 隔离库存、订单和通知。切换应用 ID 前，应先处理原应用未完成订单并保留恢复资料。

## 验证

`npm test` 的支付检查使用明确的服务端测试替身，覆盖金额篡改、权限与凭据隔离、默认库存、验签拒绝、事件分类、查询补偿、事务回滚、重复发码、长期有效/单次注册、关单与退款幂等、重启以及数据库队列。它们不替代官方沙箱付款与公网通知联调。

接口依据：[官方网页支付文档](https://aipay.alipay.com/docs/vibe-pay/ai-web-app-payment-qianyi/api-list/alipay-trade-page-pay.html)。页面跳转使用已安装 SDK 的 `pageExec(..., "GET", ...)` 生成可信跳转链接，保持全站 `form-action 'self'` 与严格脚本策略。
